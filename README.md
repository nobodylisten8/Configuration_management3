# Ассемблер и интерпретатор УВМ: вариант 1

Практическая работа № 3. Реализация на Python 3.10+ без внешних
зависимостей времени выполнения. Текущий этап: 1 из 5.

## Запуск и проверка

Из корня проекта (Windows, Linux или macOS):

```console
python -m src assemble examples/specification.asm output.bin --test
python -m unittest discover -s tests -v
python -m tools.check_quality
```

Windows: `run.bat assemble examples/specification.asm output.bin --test`.
Компиляция Python в исполняемый файл не требуется. Проверка синтаксиса:
`python -m compileall -q src tests tools`. Для проверки стиля:

```console
python -m pip install -r requirements-dev.txt
python -m ruff check .
```

## Язык ассемблера

Одна инструкция в строке: `МНЕМОНИКА аргумент, аргумент, ...`.
Мнемоники нечувствительны к регистру. Пустые строки игнорируются,
комментарий начинается с `;`. Числа: десятичные или с префиксами
`0x`, `0b`, `0o`; отрицательные числа разрешены для констант.
Метки, переходы и псевдоинструкции отсутствуют.

| Команда | Поля | Действие |
| --- | --- | --- |
| `LOAD B, C` | A=26, B:7, C:27 бит | `R[B] = C` |
| `READ B, C` | A=46, B:7, C:7 бит | `R[C] = M[R[B]]` |
| `STORE B, C, D` | A=49, B:7, C:15, D:7 бит | `M[R[D] + C] = R[B]` |
| `ABS B, C` | A=59, B:7, C:7 бит | `M[R[C]] = abs(R[B])` |

Регистры B, C, D: 0..127, смещение STORE: 0..32767.
Поскольку задание не определяет знаковость констант, принят дополнительный
код для 27-битного C: от -67108864 до 67108863. Это позволяет проверять
`abs()` на отрицательных значениях. Поля A, B, D и смещение беззнаковые.
При выводе IR отрицательное C показывается как знаковое значение.
В двоичном представлении оно будет закодировано в 27 битах.

## Этап 1: промежуточное представление

`assemble SOURCE OUTPUT [--test]`: SOURCE — текст UTF-8, OUTPUT — будущий
двоичный файл. На этом этапе файл OUTPUT не создаётся. `--test` печатает:

```text
{'A': 26, 'B': 28, 'C': 43}
{'A': 46, 'B': 9, 'C': 55}
{'A': 49, 'B': 127, 'C': 271, 'D': 20}
{'A': 59, 'B': 23, 'C': 65}
```

Файл `examples/specification.asm` воспроизводит все четыре теста задания.
Ошибки содержат номер исходной строки, CLI возвращает код 1;
ошибки аргументов CLI — код 2; успешное выполнение — код 0.

## Модули и функции

* `src.isa`: Operation, Instruction и fields описывают команды и их поля;
  validate_operands и operand_bounds проверяют допустимые значения.
* `src.parser`: parse_integer разбирает числа; parse_line — одну строку;
  parse_program — программу с диагностикой по номеру строки.
* `src.assembler`: assemble читает исходник и печатает IR в тестовом режиме.
* `src.cli`: build_parser определяет аргументы; main выполняет команду.
* `tools.check_quality`: проверяет файлы индекса Git, структуру, docstring,
  числовые литералы в сравнениях, длины, аргументы и сложность функций.
  check_commits проверяет заголовки и подробные тела коммитов.

## Требования к оформлению

Исходники в `src`, тесты в `tests`, скрипт запуска `run.bat`.
В Git не включаются двоичные файлы, архивы, окружения, кэши, файлы IDE
и артефакты сборки. Примеры результатов хранятся только как текст.
Ограничения: файл ≤1000 строк; Python ≤80 символов в строке;
остальные текстовые файлы ≤120 символов; функция ≤40 строк от `def`
до последней строки включительно, с docstring и пустыми строками;
≤7 аргументов (включая self), сложность ≤10. Все функции документированы.
Проверка сложности учитывает все вложенные if, циклы, генераторы,
обработчики исключений и логические условия. В сравнениях используются
именованные константы. Ruff дополнительно проверяет стиль PEP8 и имена.

Каждый этап — отдельный коммит `feat(stageN): ...` с подробным телом в main.
Ветки `stage1`..`stage5` указывают на окончание соответствующих этапов.
